## 1. Что делаем и что берём из прототипа

Python-прототип задаёт проверенную логику, которую переносим 1:1:
- опрос состояния кнопки через `GetAsyncKeyState(vk) & 0x8000` (без хуков);
- клик ЛКМ, пока кнопка активации **зажата** (hold-to-click), задержка 40 мс;
- idle-опрос ~10 мс, когда кнопка не зажата;
- экстренный выход по F12;
- работа в фоне через иконку в трее.

Что меняем/исправляем по сравнению с прототипом:
| Проблема прототипа | Решение в Rust-версии |
|---|---|
| Кнопка и задержка зашиты в константы | GUI: «Слушать» для выбора любой клавиши/кнопки мыши + поле задержки |
| Внешний `icon.ico`, падение без него | Иконка вшита в `.exe` через `include_bytes!` |
| `mouse_event` (legacy API) | `SendInput` с проверкой результата |
| Нет управления старт/стоп | Кнопка «Старт/Стоп» + общий статус |
| F12 объявлен, но не реализован | Отдельный watcher-поток, убивающий процесс даже при зависшем GUI |
| Нет окна вообще | Минималистичное окно egui, крестик = свернуть в трей |

## 2. Стек и зависимости (зафиксировано)

Выбор GUI: **egui + eframe** (а не Slint/Tauri) — легче всего совмещается с `tray-icon`
в одном процессе без WebView, даёт один маленький `.exe`, а immediate-mode идеально
подходит для опроса каналов и статусов.

```toml
[dependencies]
eframe   = "0.37"          # GUI-фреймворк (egui внутри)
tray-icon = "0.26"         # трей; меню — через реэкспорт tray_icon::menu (muda 0.21)
image    = { version = "0.25", default-features = false, features = ["ico"] }
anyhow   = "1"             # агрегация ошибок
log      = "0.4"
env_logger = "0.11"

[dependencies.windows]
version = "0.62"
features = [
    "Win32_Foundation",                  # GetLastError, HANDLE
    "Win32_UI_Input_KeyboardAndMouse",   # GetAsyncKeyState, SendInput, VK_*
    "Win32_UI_WindowsAndMessaging",      # GetMessageW/PeekMessageW (если понадобится), хуки — нет
    "Win32_Media",                       # timeBeginPeriod/timeEndPeriod (точность sleep)
]

[build-dependencies]
winresource = "0.1"        # иконка/метаданные в ресурсах .exe (для Проводника)
```

> Примечание: eframe 0.37 — свежая мажорная итерация; конкретные сигнатуры
> (`ViewportCommand`, `NativeOptions`, close-хуки) сверять с доками именно 0.37,
> ниже по тексту API-фрагменты даны как ориентир.

## 3. Архитектура: потоки и коммуникация

```
┌────────────────────────── Main thread ──────────────────────────┐
│  Win32 message pump (winit/eframe) + TrayIcon + muda-меню        │
│  App::update(): рисует GUI, опрашивает каналы (try_recv)         │
└──────┬──────────────────────────────────────────────▲───────────┘
       │ Arc<Mutex<Settings>> {vk, delay_ms, enabled}  │ mpsc-каналы:
       │ (GUI пишет, кликер читает)                    │  • UiEvent (Listen→Captured(vk), ShowWindow, Exit, ClickError)
       ▼                                               │  • TrayEvent (из MenuEvent/TrayIconEvent receivers)
┌──────────────── Clicker thread ────────────────┐  ┌── Emergency watcher thread ──┐
│ loop: read settings → is_pressed(vk)?          │  │ loop: GetAsyncKeyState(F12)  │
│   да → send_left_click(); sleep(delay_ms)      │  │ нажат → shutdown.store(true) │
│   нет → sleep(5–10 мс)                          │  │ → process::exit(0)           │
│ режим Listen: скан VK 0x01..0xFE → Captured(vk)│  │ (не зависит от GUI/кликера)  │
└────────────────────────────────────────────────┘  └──────────────────────────────┘
```

Правила:
- **Трей создаётся на главном потоке до `eframe::run_native`** — на Windows `tray-icon`
  требует поток с активным message pump; winit его обеспечивает. События меню/трея
  забираются из `MenuEvent::receiver()` / `TrayIconEvent::receiver()` внутри
  `App::update()` + `ctx.request_repaint_after(~100ms)`, чтобы GUI не «засыпал».
- Весь `unsafe` — только в `winapi.rs`, наружу безопасные `Result`/`bool`-обёртки.
- Кликер и watcher **не зависят** от живости GUI: остановка и экстренный выход
  работают через `AtomicBool shutdown`, даже если окно зависло.
- Кликер живёт всё время работы приложения (daemon-поток), активность гейтится
  `settings.enabled` — старт/стоп не пересоздаёт поток.

## 5. Поэтапный план

### Этап 0. Каркас проекта (~0.5 ч)
- [x] `cargo new autoclicker`, разложить пустые модули из §4, прописать `Cargo.toml` (§2).
- [x] `#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]` в `main.rs`.
- [x] Release-профиль: `lto = "thin"`, `codegen-units = 1`, `strip = true`, `panic = "abort"`.
- [x] `assets/icon.ico` (нарисовать простую иконку курсора/клика), `build.rs` с `winresource`.
- [x] `cargo check --target x86_64-pc-windows-msvc` (кросс-проверка типов; рантайм — только на Windows).

**Готово, когда:** скелет собирается (check) под Windows-таргет, структура совпадает с §4.

### Этап 1. Win32-обёртки и таблица клавиш (~1–1.5 ч)
- [x] `winapi::is_pressed(vk: u16) -> bool` — `GetAsyncKeyState`, маска `0x8000`.
- [x] `winapi::send_left_click() -> anyhow::Result<()>` — один `SendInput` c двумя
      `INPUT` (LEFTDOWN+LEFTUP) либо два вызова; проверка возвращённого числа событий,
      при ошибке — `GetLastError` в текст ошибки.
- [x] `winapi::time_begin_period(1)` / `time_end_period(1)` — точность `sleep` до ~1 мс
      (иначе `sleep(1)` на Windows фактически ~15 мс). Вызов при старте, откат при выходе.
- [x] `keys.rs`: таблица VK → имя: мышь (VK_LBUTTON 0x01, RBUTTON 0x02, MBUTTON 0x04,
      XBUTTON1 0x05, XBUTTON2 0x06), F1–F12, Space/Enter/Esc/Tab, буквы/цифры, модификаторы,
      навигация; `name_for(vk) -> String` c фолбэком `«VK 0xNN»` для неизвестных.
- [x] Юнит-тесты на `keys.rs` (без WinAPI — гоняются на любой ОС).

**Готово, когда:** unsafe инкапсулирован, наружу только безопасные функции; имена клавиш покрыты тестами.

### Этап 2. Настройки и общее состояние (~0.5 ч)
- [x] `Settings { vk: u16 (дефолт XBUTTON2, как в прототипе), delay_ms: u64 (дефолт 40, мин 1), enabled: bool (дефолт false) }`.
- [x] `SharedSettings = Arc<Mutex<Settings>>`; методы `snapshot()` (короткий лок + Copy)
      и `update(...)` с клампом `delay_ms >= 1` на обеих сторонах (GUI и кликер).
- [x] `AtomicBool shutdown` — общий флаг остановки для всех потоков.
- [x] Юнит-тесты: кламп, дефолты, конкурентный доступ (spawn + update).

**Готово, когда:** состояние разделено между потоками без гонок, дефолты из ТЗ закреплены тестами.

### Этап 3. Поток кликера + режим «Слушать» + аварийный выход (~2 ч)
- [x] `clicker::spawn(shared, ui_tx, shutdown) -> JoinHandle`:
      цикл: `shutdown` → выход; снимок настроек; если `enabled && is_pressed(vk)` →
      `send_left_click()` + `sleep(delay_ms)`; иначе `sleep(10ms)`.
      Ошибки `SendInput` → `UiEvent::ClickError` в GUI **с троттлингом** (не спамить канал),
      после N ошибок подряд — авто-стоп кликера.
- [x] Режим захвата клавиши (`UiCommand::StartListen` / атомик `listening`):
      1) дождаться, пока **все** кнопки отпущены (иначе поймаем клик по кнопке «Слушать»);
      2) сканировать VK 0x01..0xFE через `is_pressed`;
      3) первое нажатие → `UiEvent::Captured(vk)`, выйти из режима;
      4) таймаут ~10 с и отмена (Esc или повторное нажатие «Слушать») → `UiEvent::ListenCancelled`.
      В режиме захвата клики не выполняются.
- [x] `clicker::spawn_emergency_watcher(shutdown)`: опрос F12 каждые ~30 мс;
      при нажатии: `shutdown = true`, короткий grace (≤100 мс), затем `std::process::exit(0)`.
      Работает независимо от GUI. Если пользователь выбрал F12 кнопкой активации — GUI
      показывает предупреждение о конфликте.
- [x] Корректный выход по `shutdown`: `time_end_period`, завершение цикла без паник.

**Готово, когда:** hold-to-click с динамической задержкой, захват любой клавиши/кнопки, F12 убивает процесс при зависшем GUI (проверяется искусственным `loop{}` в update на тестовой сборке).

### Этап 4. GUI на egui/eframe (~2–3 ч)
- [x] Окно ~360×240, не resizable, заголовок «Автокликер», иконка из `assets` (`NativeOptions.icon_data`).
- [x] Разметка сверху вниз:
      1) строка «Кнопка активации: **[имя VK]**» + кнопка «Слушать» (в режиме ожидания —
         «Нажмите клавишу… (Esc — отмена)», мигание/спиннер);
      2) «Задержка, мс»: `DragValue` (клампом 1..=10000) + быстрый пресет-слайдер, дефолт 40;
      3) большая кнопка «Старт»/«Стоп» (цветовая индикация состояния);
      4) статус-бар: «Активен: кликаю, пока зажата X» / «Остановлен» / последняя ошибка;
      5) мелким шрифтом: «F12 — экстренный выход».
- [x] Все изменения сразу пишутся в `SharedSettings` (без кнопки «Применить»).
- [x] Обработка `UiEvent` в `update()`: `Captured` → обновить vk + имя; `ClickError` → статус-бар + `log::error!`.
- [x] Никаких `.unwrap()` в путях исполнения: ошибки инициализации — диалог/лог и выход с кодом 1.

**Готово, когда:** все три контрола ТЗ работают, настройки применяются на лету, ошибки видны в GUI.

### Этап 5. Трей и жизненный цикл окна (~2 ч) — самый рискованный этап
- [x] `tray.rs`: `build_tray() -> Result<TrayIcon>`; иконка `include_bytes!("../assets/icon.ico")`
      → `image` → RGBA → `tray_icon::Icon::from_rgba`; меню: «Показать окно», сепаратор, «Выход»;
      tooltip «Автокликер — активен/остановлен» (обновлять при старт/стопе).
- [x] Создание трея **до** `eframe::run_native` на main-потоке; `TrayIcon` держать живым
      в `App` (drop = исчезновение иконки).
- [x] В `update()`: дренаж `MenuEvent::receiver()` и `TrayIconEvent::receiver()`:
      «Показать окно» / double-click по иконке → `ViewportCommand::Visible(true)` + `Focus`;
      «Выход» → graceful shutdown (см. этап 6).
- [x] Перехват крестика: `if ctx.input(|i| i.viewport().close_requested())` →
      `ViewportCommand::CancelClose` + `Visible(false)` (окно скрыто, процесс жив).
- [x] Кнопка «Свернуть в трей» в GUI — тот же путь `Visible(false)`.
- [x] `ctx.request_repaint_after(Duration::from_millis(100))` — гарантированный опрос каналов.
- [x] План Б (если события трея не доходят в связке с winit): выделенный поток с ручным
      `GetMessageW`-циклом владеет треем и шлёт события в GUI через mpsc; eframe остаётся на main.

**Готово, когда:** крестик прячет окно; клик/меню трея возвращает его; «Выход» завершает процесс; иконка не «висит» после выхода.

### Этап 6. Склейка, graceful shutdown, логирование (~1 ч)

- [x] F12-путь намеренно «грязный» (`process::exit`) — это фича аварийного выхода, задокументировать.
- [x] Ревизия: `grep unwrap\(|expect\(` — допустимо только в тестах и доказуемо-невозможных местах с комментарием.

**Готово, когда:** оба сценария выхода корректны, логи пишутся, потоки не переживают процесс.

## 6. Риски и подводные камни (с митигацией)

| Риск | Вероятность | Митигация |
|---|---|---|
| События трея не доходят до egui (нет активного pump при скрытом окне) | средняя | `request_repaint_after(100ms)`; план Б из этапа 5 (выделенный GetMessageW-поток) |
| «Слушать» ловит собственный клик по кнопке GUI | высокая без защиты | фаза «дождаться отпускания всех кнопок» перед сканом (этап 3) |
| `sleep(1)` фактически ~15.6 мс (таймер Windows) | высокая | `timeBeginPeriod(1)`; при желании — спин-гибрид для delay < 5 мс (отмечено как опция) |
| Клик по egui-кнопке «Стоп» симулирует лишний ЛКМ-клик поверх GUI | низкая | кликер не кликает, когда кнопка активации — та же, что использует пользователь в GUI; допустимо, задокументировать |
| SendInput не работает в elevated-окнах (UIPI) | точно будет | не баг: документировать; опция «запуск от администратора» вне scope |
| Антивирусы/SmartScreen флагуют автокликер | средняя | подпись вне scope; README-примечание, чистый код без обфускации |
| API eframe 0.37 отличается от примеров в сети | средняя | сверяться с доками 0.37 на этапе 0, изолировать viewport-логику в `app.rs` |
| Гонки настроек | низкая | короткий лок + snapshot; задержка/кнопка — Copy-типы |
